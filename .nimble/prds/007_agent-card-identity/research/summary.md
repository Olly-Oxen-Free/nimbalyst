# Research Summary — agent-card-identity

Two pre-existing, confirmed bugs in `packages/runtime/src/ui/AgentTranscript/components/RichTranscriptView.tsx`.

**A1 — spawn cards render expanded by default, headers diverge by kind.** Root cause: an unbounded auto-expand `useEffect` (lines 1626-1642, from commit `769a3ede5`, 2026-04-02) that adds every subagent message's id to `expandedTools` and never removes it — `subagentId` and the card's own lookup key are the same `toolUseId`, so every Task/teammate spawn mounts expanded. Fix: delete the effect (collapsed-by-default is intended). Separately, `TaskToolWidget.tsx`'s header (plain Task/Agent spawns, built by PRD 004) has no icon, no model/effort label, no live status, and no chevron, while the generic teammate/sub-agent card (`RichTranscriptView.tsx:1839-1973`) has all four — despite both having the same underlying data (`message.subagent.model`, a status source). Fix: extract the audit-label and status-indicator logic into a shared piece both consume, preserving the class-name selectors (`.rich-transcript-tool-card.sub-agent/.teammate`, `.task-tool-widget-header`) that existing tests key on.

**A2 — spawned-agent headers show generic "Claude Agent".** Root cause: `getProviderDisplayName(provider)` (`RichTranscriptView.tsx:2298-2300`) is driven by a single `provider` prop per `RichTranscriptView` mount; embedded sub-agent transcript views (`TeammateThreadPopover.tsx`, `TaskToolWidget.tsx`) never pass one, so assistant turns inside them show the generic label instead of the specific agent's name/model, both of which are already available locally at those call sites but never forwarded. Fix: add an optional override prop (e.g. `senderLabel`) to `RichTranscriptViewProps`, wire `teammate.name`/`teammate.model` and `agentType`/`message.subagent?.model` through from the two confirmed call sites. Two more `RichTranscriptView` mounts (`TaskThreadPopover.tsx`, `TaskTileRail.tsx`, `TeammateTileRail.tsx`) were located but not read this pass — verify before finalizing the call-site list.

No test currently asserts the auto-expand behavior or the header-anatomy divergence, so both fixes are safe to make without breaking existing coverage, provided load-bearing class-name selectors are preserved. External research was skipped (internal-only mode); no third-party library or API decision is in scope.
